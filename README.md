# TaskFlow

TaskFlow is a multithreaded task processing and job scheduling system with a
C++17 backend.

## Project Structure

- `backend/include/`: Public backend headers.
- `backend/src/`: Backend source files.
- `frontend/`: React and Vite operations dashboard.
- `tests/`: Future automated tests.
- `docs/`: Project and design documentation.

## Build and Run

The backend uses CMake FetchContent to fetch pinned versions of
[cpp-httplib](https://github.com/yhirose/cpp-httplib) for HTTP,
[nlohmann/json](https://github.com/nlohmann/json) for JSON, and the official
[MongoDB C++ driver](https://github.com/mongodb/mongo-cxx-driver) 3.11.1. The
driver build fetches MongoDB C Driver 1.30.6. No separate driver package
installation is needed; the initial configure requires network access, CMake,
and C/C++ toolchains.

Install and start MongoDB Community Server using the
[official installation instructions](https://www.mongodb.com/docs/manual/installation/).
Then set the connection URI in the environment; credentials should be provided
only through this environment variable or a secret manager, never committed:

```bash
export TASKFLOW_MONGODB_URI='mongodb://localhost:27017'
cmake -S backend -B backend/build
cmake --build backend/build --parallel
./backend/build/taskflow_engine
```

For an authenticated deployment, set `TASKFLOW_MONGODB_URI` to that deployment's
MongoDB URI without placing it in source control. The server verifies the
connection and ensures the database index during startup. It listens on
`http://127.0.0.1:8080`.

The API listens on `http://127.0.0.1:8080` and runs three workers. Stop it with
Ctrl+C; the server stops accepting requests, then the worker pool drains queued
jobs and joins its threads.

Run the in-memory API, priority, and retry checks with:

```bash
ctest --test-dir backend/build --output-on-failure
```

These tests do not require MongoDB. MongoDB-backed runtime operations require a
reachable server and the URI configured above.

## REST API

`POST /jobs` requires a non-empty string `payload` and a `priority` of `HIGH`,
`MEDIUM`, or `LOW`. The response is HTTP 201 with the assigned ID and initial
PENDING status:

```bash
curl -i -X POST http://127.0.0.1:8080/jobs \
  -H 'Content-Type: application/json' \
  -d '{"payload":"Generate monthly report","priority":"HIGH"}'
```

```json
{"id":1,"status":"PENDING"}
```

Use `GET /jobs` for all tracked jobs, `GET /jobs/{id}` for one job, and
`GET /stats` for live status counts:

```bash
curl http://127.0.0.1:8080/jobs
curl http://127.0.0.1:8080/jobs/1
curl http://127.0.0.1:8080/stats
```

The API rejects malformed requests and unsupported priorities with HTTP 400;
unknown job IDs return HTTP 404. MongoDB errors return HTTP 503. Submit
`FAIL_ONCE` or `FAIL_ALWAYS` as the payload to observe retry success or terminal
failure in job details and stats.

## Frontend Dashboard

The React dashboard uses Vite, Tailwind CSS, and Lucide React. It displays live
job statistics and jobs from the API, supports job submission and detail
inspection, and refreshes automatically every two seconds. No sample jobs or
statistics are generated by the frontend.

Start the backend with MongoDB available as described above, then run the
dashboard in another terminal:

```bash
cd frontend
npm install
npm run dev
```

Open the local URL printed by Vite (typically `http://localhost:5173`). The
development server proxies `/api` requests to `http://127.0.0.1:8080`, avoiding
a separate CORS configuration. Set `TASKFLOW_API_PROXY_TARGET` before starting
Vite to change the development proxy target. For a built frontend, set
`VITE_API_BASE_URL` to the API base URL before building (for example,
`VITE_API_BASE_URL=http://127.0.0.1:8080 npm run build`); it defaults to `/api`.

Create a production bundle with:

```bash
npm run build
```

## MongoDB Persistence

Jobs are stored in the `taskflow` database and `jobs` collection. The unique
ascending index on `id` is created at startup. A job document has this shape
(MongoDB BSON types shown):

```javascript
{
  _id: ObjectId("..."),
  id: NumberInt(1),
  payload: "Generate monthly report",
  priority: "HIGH",
  status: "PENDING",
  attempts: NumberInt(0),
  createdAt: ISODate("2026-10-09T05:00:00.000Z"),
  updatedAt: ISODate("2026-10-09T05:00:00.000Z")
}
```

`createdAt` and `updatedAt` are BSON Date values in UTC, with millisecond
precision. Job status and attempts are written to MongoDB whenever a worker
starts processing, schedules a retry, completes a job, or marks terminal
failure. The repository uses the official driver's connection pool; MongoDB
statistics are calculated using an aggregation over persisted statuses.

At startup, the repository loads stored jobs into a synchronized snapshot for
API access and chooses the next integer ID after the highest existing ID.
Find/list operations refresh from MongoDB; updates are written to MongoDB
before updating the in-memory snapshot. The application does **not**
automatically re-enqueue jobs left PENDING or PROCESSING after a crash. Those
documents remain visible with their last stored status until an explicit
recovery policy is implemented; a PROCESSING status does not prove whether its
external work completed before the crash. State is persistent across
application restarts, but current in-memory queue contents and execution
progress are not. If MongoDB becomes unavailable during execution, workers log
the persistence error and requeue the job while the service is running. During
shutdown they stop retrying failed persistence operations and exit; the job
remains at its last successfully persisted status for later inspection.

The repository is the persistence boundary: HTTP handlers and workers depend
on its operations rather than containing MongoDB queries. `JobRegistry`
remains as a thread-safe in-memory implementation for engine tests.

## Priority Scheduling

The thread-safe job queue uses a `std::priority_queue`, ordered by job priority
and then by an enqueue sequence number. Higher-priority jobs are dequeued
first, while sequence numbers preserve FIFO order among jobs of equal
priority. Multiple workers can execute dequeued jobs concurrently, so their
completion messages are not guaranteed to appear in dequeue order.

## Retry Handling

The worker pool defaults to a maximum of three processing attempts; this limit
can be configured when constructing the pool. A job's attempt count records
attempts started, not retries performed. Failed jobs are retried with their
original priority and a new queue sequence number, using a short exponential
backoff. `FAIL_ONCE` fails once and then succeeds; `FAIL_ALWAYS` fails on every
attempt. Exhausted jobs are reported as FAILED. This in-memory terminal-failure
record is not a persistent dead-letter queue.

## CMake

`backend/CMakeLists.txt` configures the backend as a C++17 project, fetches the
pinned HTTP, JSON, and official MongoDB C++ driver dependencies, and defines
the `taskflow_engine` and API test executables.
